## 第二部分：功能与技术架构说明书（卓越版）


### 一、技术架构与开发规范指导

为了确保本系统不仅在业务逻辑上卓越，在代码工程化层面同样达到企业级标准，项目开发过程中需严格遵循以下技术边界与架构规范：

#### 1. 强化核心业务的结构化抽象（OOD & 领域模型）

在编写 JavaBean 实体类时，必须坚决摒弃"贫血模型"（只有 Getter/Setter 的简单数据载体）。建议严格按照面向对象设计（OOD）和 UML 标准，将具体的业务行为内聚在对象内部。

- **职责明确**：例如 HotelOrder（总订单）对象除了包含基础属性外，应自带 `calculateTotalAmount()`（总金额计算）、`cancelOrder()`（状态流转验证）等方法，明确类与对象的职责，确保它们作为高质量的结构化抽象独立存在。

#### 2. 前端展示与打印技术的选型明确

系统需要应对复杂的数据可视化与报表输出，技术选型如下：

- **统计图表展示**：前端数据看板（如月度入住率、房型收益占比）统一集成 ECharts 进行渲染，保证图表的交互性与美观度。
- **网页式打印功能**：采用原生 CSS 的 `@media print` 媒体查询技术。在打印模式下自动隐藏侧边导航栏、操作按钮等无关元素，确保打印出的水单干净、专业。
- **原生文件导出**：对于复杂的财务对账单和统计表，在服务端引入 Apache POI 库，将查询到的结果集直接导出为原生 Excel 文件，完美契合酒店财务人员的日常操作习惯。

#### 3. 明确服务端与前端的边界划分（职责分离）

本系统包含了诸如"团队一键排房"、"高并发防超卖校验"以及"前台交接班结账核算"等重度数据处理与事务控制逻辑。为了保障系统的健壮性和开发效率：

- **服务端（Server 端）攻坚**：这类高度复杂的聚合逻辑和底层数据库交互（如悲观/乐观锁控制、多表联查与更新），将全权交由负责 Server 端开发的伙伴去集中攻坚和保障。
- **前端（JSP 视图层）聚焦**：前端同学则完全解脱出来，专注于 JSP 视图的动态数据绑定、Ajax 异步交互、表单校验以及整体 UI 操作体验的极致优化。

### 二、核心业务功能模块详述

#### 1. 系统与权限管理模块（System & Auth）

这是系统的底座，确保数据安全和操作合规。

- **角色与权限控制**：管理员可动态维护"系统角色"（如店长、前台、财务），并为不同角色分配独立的操作界面和权限。结合前端路由，实现"千人千面"的操作控制。
- **员工账号管理**：维护员工账号信息，支持账号启用/禁用状态切换。增加密码复杂度校验机制，保障系统入口安全。
- **全局数据字典维护**：动态管理系统内的所有下拉选项（如房态、款项类型），拒绝代码硬编码。提供可视化的字典配置界面。
- **系统操作审计日志（扩展设计）**：全局记录敏感操作（如手动改价、删除预订），防范内部管理风险。

#### 2. 客户关系管理模块（CRM）

负责沉淀酒店的核心客户资产。

- **客户档案管理**：录入并维护客户的基本信息及会员等级（VIP），支持通过姓名、手机号等进行模糊查询。
- **合规同住人登记**：满足公安联网要求，对所有实际入住客人的身份证进行实名登记。
- **客史偏好管理（扩展设计）**：记录客人的历史入住习惯（如要求无烟房、高楼层）。同时设立黑名单机制，拦截有过恶意损坏记录的预订请求。

#### 3. 客房与客务管理模块（Housekeeping）

对酒店核心资产（房间）的生命周期和状态进行精细化管控。

- **房型与客房设置**：维护各类房型的基础挂牌价及床位数，并生成具体的物理房间号及楼层信息。
- **实时房态监控**：前台可通过房型、空闲状态等条件进行组合查询，快速锁定可用房间。界面采用直观的色块"房态盘"进行展示。
- **客务与维修派单**：记录房间打扫（脏房转净房）和设备维修（维修中转空闲）的工单，跟踪处理人及完成时间。阿姨打扫完毕后一键切换房态，立即释放可售库存。

#### 4. 订单与前台接待模块（Front Desk）

系统的业务心脏，处理核心业务流转，具备高并发下的防超卖控制。

- **客房预订管理**：处理客人的预订请求，锁定预计到店和离店时间，管理预订状态。支持定金收取与保留时间设置。
- **入住办理（Check-in）**：支持预订转入住，同时也完美兼容无预订的直接步入式（Walk-in）散客入住。自动校验版本号（乐观锁）杜绝一房多卖。
- **退房办理（Check-out）**：结束入住流程，释放房间状态（自动从"已入住"变更为"空闲脏房"）。
- **异常与高级业务流转（扩展设计）**：完美处理客人入住后因设施故障要求"换房"的逻辑，以及处理团队（Group）客人的"批量办理入住"功能。

#### 5. 财务与报表分析模块（Finance & Reports）

满足需求文档中要求的统计、导出与打印功能，账目清晰可查。

- **总订单结算收银**：以"总订单"为核心归集所有消费，计算产生总额。打破物理房间结账的局限性，支持多房合结。
- **精细化账目追踪**：记录每一笔款项的明细（如房费、押金、违约金、赔偿金等），支持正数收款与负数退款。完美处理客人爽约（No-Show）时定金转违约金的平账逻辑。
- **多维度统计与导出**：按日期范围统计营收，将查询到的结果集按列排序，生成可用于网页打印、导入导出的统计报表。
- **前台交接班结账（扩展设计）**：严格的财务隔离机制，收银员下班系统自动核算本班次收支明细单，核对无误后打印签字，做到日清月结。

## 第三部分：数据库设计说明书（完整修正版）


### 一、数据库设计准则与规范

本系统基于 Oracle 数据库设计。为了满足高并发需求、权限隔离、复杂模糊查询及严谨的财务统计，本设计严格遵循以下底层机制：

- **逻辑删除（Soft Delete）**：核心业务表均包含 `IS_DELETED (NUMBER(1) DEFAULT 0)` 字段。严禁物理删除核心数据，确保历史财务统计和订单记录的绝对完整。外键约束统一采用 `ON DELETE RESTRICT`（拒绝删除）策略。
- **乐观锁并发控制（Optimistic Locking）**：核心业务表（如客房、订单）包含 `VERSION (NUMBER(10) DEFAULT 0)` 字段。在处理预订、状态更新时，通过比对版本号防止"一房多卖"等并发问题。
- **完整审计追溯（Audit Fields）**：所有核心可变业务表均包含以下字段：
  - `CREATE_TIME`：数据创建时间
  - `UPDATE_TIME`：数据最后更新时间
  - `UPDATE_BY`：执行最后一次更新操作的管理员或员工 ID（关联 SYS_USER）
- **状态字典化**：所有状态标识（如房态、订单状态）均通过 SYS_DICT 表映射为数字，杜绝在数据库中硬编码中文字符串。

### 三、数据库查询与索引优化方案（Indexing）

本系统在 Oracle 数据库层面设计以下 B-Tree 索引策略：

- **核心模糊查询索引**：为 `CUSTOMER.CUST_NAME` 和 `CUSTOMER.PHONE` 建立普通索引，支持高效模糊匹配；为 `ID_CARD` 建立唯一索引。
- **多条件房态组合索引**：为 `ROOM (TYPE_ID, STATUS)` 建立联合复合索引，优化前台"指定房型且空闲"的检索效率。
